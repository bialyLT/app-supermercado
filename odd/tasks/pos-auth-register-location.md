## Findings (candidate worktree at HEAD 5031d17)

### Authentication and API authority
- Real browser observation: anonymous `GET /pos` returns 200 and renders the sales screen. Anonymous `GET /api/pos/context` and `GET /api/pos/catalog` return 401. Existing checkout/mutation APIs remain server-session protected. Thus there is no observed unauthenticated sale, but the route exposes an unusable POS shell and misleads the cashier.
- `app/pos/page.tsx` is a client page without a server auth boundary. `proxy.ts` only applies CSP; it does not authenticate. `app/admin/layout.tsx` is a relevant existing server-side redirect-to-`/` pattern.
- Current `tests/e2e/pos.spec.ts` explicitly expects the keyboard/touch POS shell to render without logging in. This test contract must change if the owner wants `/pos` protected.
- `/api/pos/context` calls stock-oriented `getOperationalContext`; `src/server/repositories/context.ts` rejects CASHIER and SUPERVISOR even after `cash.read` authorization, leading to `REQUEST_FAILED`/400. Prior real login showed API mutations were separately denied without a session. Do not grant inventory-write permissions to fix POS context.

### Register/location authority
- Current Prisma `CashRegister` has tenant + branch + name, but no location relation. `CashRegisterSession` has register + branch + user + currency/open/close fields, but no location snapshot.
- No register-configuration screen or API exists; cash-shifts currently accepts a free-text register UUID.
- Wave 0 S7 mandates one active authorized location and blocks zero/multiple. In response to the prior recommendation, the owner said «ok» and added S2; this accepts a caja→ubicación mapping as the intended alternative, but the exact mechanism/administrative UI is not yet specified in code or decisions.
- The owner selected «ADMIN + snapshot al abrir turno (recomendada)». Decision: only ADMIN manages assignment; each register has one explicit active location in the same branch; at session open, snapshot the assigned location and use that immutable session location for all sales in that shift. Later remapping applies to future shifts. No cashier selector or arbitrary fallback; nullable migration; unassigned registers fail closed. Existing demo DB has 2 branches, 4 locations, 3 registers and one open session; retain all data, make explicit demo-only assignments and establish a new session through supported flows; no reset/drop.
